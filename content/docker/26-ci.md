# 26 — CI'da Docker

[← Oldingi: Registry va teglash](25-registry.md) · [Mundarija](README.md)

## Tushuncha

**CI** (continuous integration — uzluksiz integratsiya) — har `push` yoki pull request'da kodni avtomatik yig'ish va tekshirish. Docker uchun bu: image'ni CI serverida yig'ish, sinash va registry'ga yuborish (25-bob). Serverga esa tayyor image tushadi (27-bob) — serverda `docker build` shart emas.

Docker hujjati (GitHub Actions) Docker'ning rasmiy action'larini beradi. Asosiylari:

| Action | Vazifasi |
| --- | --- |
| `docker/metadata-action` | Git ma'lumoti va GitHub hodisasidan teglar, label'lar, annotatsiyalar yasaydi |
| `docker/login-action` | Registry'ga kirish |
| `docker/setup-buildx-action` | BuildKit builder'ini yaratadi (13-bob) |
| `docker/build-push-action` | BuildKit bilan yig'ish va yuborish |
| `docker/setup-qemu-action` | Multi-platform build uchun QEMU (13-bob) |

Hujjatdagi joriy versiyalar: `metadata-action@v6`, `login-action@v4`, `setup-buildx-action@v4`, `build-push-action@v7`, `setup-qemu-action@v4`.

> **Eslatma.** Bu bobdagi workflow fayllari — rasmiy hujjatdagi misollar; ular ushbu kitob uchun GitHub'da **ishga tushirib ko'rilmagan** (alohida repozitoriy va registry hisobi kerak). Bobdagi kesh tajribasi esa serverda haqiqiy bajarildi.

## Boshlash: Docker Hub'ga yig'ish va yuborish

Hujjatdagi tayyorgarlik: repozitoriy **Settings → Secrets and variables → Actions** da `DOCKERHUB_TOKEN` (secret — Docker Hub access token) va `DOCKERHUB_USERNAME` (variable). Fayl — `.github/workflows/docker-ci.yml`:

```yaml
name: Build and push Docker image

on:
  push:
    branches:
      - main
  pull_request:

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Extract Docker image metadata
        id: meta
        uses: docker/metadata-action@v6
        with:
          images: ${{ vars.DOCKERHUB_USERNAME }}/my-image

      - name: Sign in to Docker Hub
        if: github.event_name != 'pull_request'
        uses: docker/login-action@v4
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v4

      - name: Build and push Docker image
        uses: docker/build-push-action@v7
        with:
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          annotations: ${{ steps.meta.outputs.annotations }}
```

Hujjatdagi izohlar:

- Pull request'da image **yig'iladi, lekin yuborilmaydi** va registry'ga kirilmaydi — secret kerak emas (fork'lardan kelgan PR'lar uchun ham).
- `checkout` qadami yo'q: `build-push-action` standart holatda **Git kontekst**ini ishlatadi — BuildKit repozitoriyni hodisa sodir bo'lgan Git havolasida (ref) o'zi oladi. Oldingi qadamlarda fayllarga kiritilgan o'zgarishlar hisobga olinmaydi.
- `main` ga push — `DOCKERHUB_USERNAME/my-image:main` tegi.
- `permissions: contents: read` — workflow token'iga minimal huquq.

## GHCR'ga: `GITHUB_TOKEN` bilan

GitHub hujjati (Publishing Docker images): GHCR uchun alohida token shart emas — workflow'ning `GITHUB_TOKEN` i yetadi, faqat job'ga `packages: write` huquqi beriladi. Hujjatdagi misoldan GHCR qismi:

```yaml
    permissions:
      packages: write
      contents: read
    steps:
      - name: Log in to the Container registry
        uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
```

Image nomi — `ghcr.io/${{ github.repository }}` (`ghcr.io/OWNER/REPO`). Workflow'dan yuborilgan image repozitoriyga avtomatik bog'lanadi (25-bob).

## Teglar: `metadata-action`

Docker hujjati (Manage tags and labels) — teglarni qo'lda yozmasdan, hodisaga qarab yasash:

```yaml
      - name: Docker meta
        id: meta
        uses: docker/metadata-action@v6
        with:
          images: |
            ghcr.io/username/app
          tags: |
            type=schedule
            type=ref,event=branch
            type=ref,event=pr
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=semver,pattern={{major}}
            type=sha
```

| Qoida | Qachon | Teg (misol) |
| --- | --- | --- |
| `type=ref,event=branch` | Branch'ga push | `main` |
| `type=ref,event=pr` | Pull request | `pr-2` |
| `type=semver,pattern=…` | `v1.2.3` git tegi | `1.2.3`, `1.2`, `1` va `latest` |
| `type=sha` | Har doim | `sha-90dd603` |

Bu — 25-bobdagi teg strategiyasining avtomatlashtirilgani: `v1.2.3` git tegi qo'yilsa, `1.2.3`, `1.2` va `1` teglari bitta image'ga tushadi. README: `latest` standart holatda (`flavor: latest=auto`) `type=semver` va git tegi qoidalari uchun **avtomatik** qo'shiladi — o'chirish uchun `flavor: latest=false`. (Teg nomlari misollari `metadata-action` README'sidan.)

## Kesh

CI runner har safar **toza** mashinada ishlaydi — 9-bobdagi build keshi yo'q. Docker hujjati (GitHub Actions: Cache) yechimlari:

| Kesh | `cache-from` / `cache-to` | Qayerda saqlanadi |
| --- | --- | --- |
| GitHub cache | `type=gha` / `type=gha,mode=max` | GitHub Actions keshi (faqat workflow ichida ishlaydi) |
| Registry | `type=registry,ref=user/app:buildcache` / `…,mode=max` | Registry'da alohida teg |
| Inline | `type=registry,ref=user/app:latest` / `type=inline` | Image'ning o'zida |

```yaml
      - name: Build and push
        uses: docker/build-push-action@v7
        with:
          push: true
          tags: user/app:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

`mode` (Docker hujjati, Cache storage backends): `min` (standart) — faqat yakuniy image'ga kiradigan qatlamlar keshlanadi; `max` — **barcha** qatlamlar, oraliq bosqichlarniki ham (multi-stage'dagi `builder`). `min` kichikroq, `max` — ko'proq kesh mos tushishi ehtimoli.

Hujjatdagi cheklov: `issue_comment`, `pull_request_target` kabi hodisalarda (va `pull_request` `types: [closed]` da) GitHub keshiga faqat **o'qish** huquqi beriladi — `cache-to: type=gha` `failed to reserve cache` xatosi bilan tugashi mumkin. Bunday workflow'larda faqat `cache-from` qoldiriladi.

### Serverda sinab ko'ramiz: registry keshi

"Toza runner" holatini serverda yasaymiz: yangi BuildKit builder (`docker-container` drayveri, 13-bob) — o'z keshi bo'sh. 25-bobdagi lokal registry va 23-bobdagi SPA loyihasi:

```text vps

ci1
$ time docker buildx build --builder ci1 --progress=quiet --cache-to type=registry,ref=localhost:5000/spa:buildcache,mode=max -t localhost:5000/spa:1 --push .

real	0m27.274s
user	0m0.237s
sys	0m0.117s
$ docker buildx rm ci1

```

## Yuborishdan oldin sinash

Docker hujjati (Test before push) — image avval sinaladi, faqat keyin yuboriladi:

```yaml
name: ci

on:
  push:

env:
  TEST_TAG: user/app:test
  LATEST_TAG: user/app:latest

jobs:
  docker:
    runs-on: ubuntu-latest
    steps:
      - name: Login to Docker Hub
        uses: docker/login-action@v4
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Set up QEMU
        uses: docker/setup-qemu-action@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v4

      - name: Build and export to Docker
        uses: docker/build-push-action@v7
        with:
          load: true
          tags: ${{ env.TEST_TAG }}

      - name: Test
        run: |
          docker run --rm ${{ env.TEST_TAG }}

      - name: Build and push
        uses: docker/build-push-action@v7
        with:
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ env.LATEST_TAG }}
```

- `load: true` — image runner'dagi Docker'ga yuklanadi (registry'ga emas), `docker run` bilan sinaladi.
- `Test` qadami xato bilan tugasa, keyingi `Build and push` qadami bajarilmaydi — image yuborilmaydi (GitHub hujjati: qadamlarga standart holatda `success()` sharti qo'llanadi).
- Hujjat izohi: ikkinchi qadamda `linux/amd64` qayta yig'ilmaydi — birinchi qadamning ichki keshidan olinadi; faqat `linux/arm64` yig'iladi.

## Tipik xatolar

**1. Pull request'da `push`.**
Tekshirilmagan kod image bo'lib registry'ga tushadi; PR'da kirish uchun secret'lar ham kerak bo'lib qoladi.
To'g'risi: hujjatdagidek `push: ${{ github.event_name != 'pull_request' }}`.

**2. Teglarni qo'lda yozish (`latest` faqat).**
To'g'risi: `metadata-action` — branch, semver va `sha` teglari.

**3. CI'da kesh yo'q.**
Har build noldan.
To'g'risi: `cache-from`/`cache-to` (`gha` yoki `registry`), `mode=max`.

**4. Token'ni workflow fayliga yozish.**
To'g'risi: repozitoriy secret'lari; GHCR uchun — `GITHUB_TOKEN` va `packages: write`.

## Amaliyot

Savollar:

1. Nega hujjatdagi workflow pull request'da image'ni yubormaydi?
2. `build-push-action` da nega `checkout` qadami shart emas?
3. `v2.1.0` git tegi qo'yilganda semver qoidalari qaysi teglarni yasaydi?
4. `mode=min` va `mode=max` farqi?
5. `load: true` nima uchun?

<details>
<summary>Javoblar</summary>

1. Tekshirilmagan kod registry'ga tushmasin va PR'da secret kerak bo'lmasin (hujjat: fork'lardan kelgan PR'lar uchun ham) — yig'ish tekshiruv sifatida qoladi.
2. Standart holatda Git kontekst: BuildKit repozitoriyni hodisaning Git havolasida o'zi oladi.
3. `2.1.0`, `2.1`, `2` va (`latest=auto` tufayli) `latest`.
4. `min` — faqat yakuniy image qatlamlari; `max` — oraliq bosqichlar bilan barcha qatlamlar.
5. Image'ni runner'dagi Docker'ga yuklab, `push` dan oldin `docker run` bilan sinash.

</details>
